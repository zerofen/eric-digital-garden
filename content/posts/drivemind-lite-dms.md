驾驶员监测系统（Driver Monitoring System，DMS）真正困难的地方，并不是在一帧画面里找到一张脸。系统还要回答更接近真实驾驶的问题：驾驶员只是短暂眨眼，还是已经持续闭眼？一次低头是正常操作，还是注意力长时间离开道路？检测到手机以后，应该立刻提醒，还是结合行为持续时间再判断？

**DriveMind Lite** 是围绕这些问题完成的一套端侧 DMS 原型。它复用我训练出的 23 点人脸关键点模型、头部姿态估计和 YOLO11 行为检测权重，把模型输出继续加工成连续风险、触发原因、安全建议和结构化报告。项目的重点不是训练一个更大的模型，而是把感知、判断、解释和展示连成一个可以运行的闭环。

## 系统要完成的，不只是“看见”

整个处理链路可以概括为：
![DMS 框架](/images/drivemind/DMS框架.png)


感知层有两条支路。第一条先用 YOLOv5Face ONNX 找到驾驶员人脸，再将裁剪后的人脸缩放，送入部署形态的 PFLD-GhostOne，得到 23 个二维关键点。随后选择其中 8 个点进行 PnP 头姿估计，得到俯仰、偏航和翻滚角。眼部与嘴部关键点还会计算 EAR、MAR，用来识别闭眼、张嘴和疑似哈欠。

第二条支路使用 YOLO11 检测座舱行为，当前支持手机、抽烟、喝水、普通眼镜和墨镜等类别。两条支路最终会被适配成统一的帧级结果，再进入状态提取模块。

![DriveMind Lite 检测到测试假人使用手机，并给出高风险提示](/images/drivemind/phone_risk.png)

这张测试结果里，系统同时画出了人脸、关键点和手机目标，并将“使用手机”映射为风险事件。右侧面板不仅显示分数，还说明了触发原因和建议动作。对使用者来说，可解释的信息往往比一个孤立的分类标签更有用。

## 从一帧状态到一段风险

单帧检测很容易抖动。光照变化、遮挡和瞬时姿态都可能让某一帧越过阈值，如果每次都立即报警，系统很快就会变得令人厌烦。

DriveMind Lite 用一个 30 秒滑动窗口保存近期状态。每种事件可以分别配置出现比例、最短持续时间和最小统计窗口。例如，闭眼在窗口中的触发比例为 `0.20`，疑似哈欠为 `0.10`；两者也各有自己的持续时间条件。风险引擎只有在“比例达到阈值”或“连续持续时间达到阈值”时，才会把状态升级为活动风险事件。

![测试假人当前帧被识别为闭眼，但尚未达到持续风险触发条件](/images/drivemind/eyes_closed.png)

上图很好地说明了这个区别：当前帧已经识别为闭眼，但持续条件尚未满足，因此风险分仍为 0。界面保留了当前状态，同时明确告诉使用者为什么没有触发风险。这种“状态”和“事件”的分离，是时序层存在的意义。

风险分并不是把所有数字简单相加。系统先取活动事件中最高的基础分，加上持续时间奖励，再叠加组合风险奖励，最后限制在 100 分以内：

```text
风险分 = max(事件基础分 + 持续时间奖励) + 组合风险奖励
```

例如，手机基础分为 70，闭眼为 55，疑似哈欠为 60；持续 1、2、4 秒会获得不同级别的奖励。“闭眼 + 哈欠”“手机 + 转头”“低头 + 人脸丢失”等组合还会额外加分。最终分数被分成低、中、高、极高四级。为了避免历史状态残留造成矛盾，风险引擎还会参考最新一帧：当前已经不再发生的事件不会继续报警，低头和抬头、左转和右转也会互相抑制。

## 报告层保持离线可用

在风险结果之上，项目提供了一层结构化安全报告。默认报告由本地确定性逻辑生成，会整理风险摘要、关键证据、事件持续时间、置信度和干预建议，因此断网时依然可以工作。

系统也预留了 OpenAI 兼容模型接口，用来润色最终报告。外部模型调用失败时，视觉推理和本地报告不会被拖垮。这种设计让语言模型承担表达增强，而把核心风险判断留在可检查、可复现的规则链路里。

## 为实时交互做的工程取舍

项目提供 FastAPI + HTML 演示界面，支持内置样例、图片和视频上传，也能读取浏览器摄像头进行连续分析。图片和离线视频逐帧执行完整检测；摄像头模式更重视“看到最新画面”，因此采用了几项不同的策略：

- YOLO 默认每 3 帧执行一次，中间帧复用最近一次检测结果；
- 实时接口返回紧凑 JSON，省略界面不会读取的关键点、检测框和时序历史；
- 标注画面通过二进制 JPEG 单独获取，避免把大尺寸 Base64 塞进每次 JSON 响应；
- 推理任务进入工作线程，健康检查、停止会话等接口仍能及时响应；
- 视频分析会保存结果视频、CSV 事件日志和 JSON 明细，方便复盘。

这里的原则很朴素：实时系统追求的不是让每个模块都以相同频率运行，而是在可接受的计算量下尽量保持结果新鲜。

## 性能测试让我重新认识了瓶颈

 2026 年 7 月集成测试使用 Ryzen 9 7945HX、RTX 4060 Laptop、10 张 `1280 × 720` 演示图，按 batch 1、FP32 循环测量。该测试每帧完整运行三套视觉模型和可视化，没有启用摄像头模式的隔帧 YOLO 等优化。

| 阶段                          |  GPU 平均时延 |  CPU 平均时延 |
| ----------------------------- | ------------: | ------------: |
| 人脸检测 + 23 点关键点 + 头姿 |     111.81 ms |     137.88 ms |
| YOLO11 行为检测               |      13.78 ms |      28.65 ms |
| 状态、时序、风险与报告        |       0.29 ms |       0.29 ms |
| 可视化绘制                    |      71.95 ms |      53.13 ms |
| **整帧总耗时**                | **197.83 ms** | **219.94 ms** |
| **换算吞吐**                  |  **5.05 FPS** |  **4.55 FPS** |

最有价值的发现，是瓶颈并不只在模型。GPU 内核中的人脸检测与关键点推理合计约 17 ms，但候选框的 Python 逐行过滤、Pillow/NumPy 图像预处理、NMS 和数据搬运占用了更多时间。可视化阶段每写一行中文都进行整幅图的颜色空间转换，也带来了 53～72 ms 的开销。

这解释了为什么换成 GPU 后，整帧速度没有像单模型数据那样成倍提升。PFLD-GhostOne 单独使用 ONNX Runtime CUDA 时平均只需 1.81 ms，但把它放进完整链路以后，前后处理和绘制决定了最终体验。对于端侧项目，优化分析必须覆盖整条数据通路，不能只看模型推理表。

另一个需要注意的数字是冷启动：GPU 首帧约 4.42 秒，CPU 首帧约 0.34 秒。CUDA 上下文、cuDNN 初始化、ONNX Runtime CUDA 会话和第一次显存分配都集中发生在首帧。长时间实时运行可以摊薄这项成本，单张图片或间歇调用则可能反而更适合 CPU。

## 当前边界与下一步

DriveMind Lite 目前是一套研究与展示性质的原型，还不能当作量产车载安全系统。风险阈值需要在更多真实驾驶数据、不同光照、遮挡、摄像头角度和人群上重新标定。

下一步最明确的工程优化，是把 25,200 个候选框的 Python 循环向量化、减少整图颜色转换，并重写人脸裁剪预处理。算法层则可以在获得可靠时序数据后，再比较 GRU、TCN 或轻量 Transformer 与当前规则系统的表现。此外，我很想训练一个集关键点、视线以及行为检测一体的模型，正在抽空进行中...

做完这个项目后，我最大的感受是：**一个能工作的 AI 系统，价值通常藏在模型之间。** 把输入接进来，把不同模型的输出对齐，把瞬时状态变成连续判断，把结果解释清楚，并且诚实地写下性能口径与能力边界——这些工作共同决定了原型是否真正可用。
